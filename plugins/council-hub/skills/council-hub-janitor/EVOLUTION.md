## 2026-10-25: what archive_room does, bulk-pass order

- **Trigger:** A real pass over the nous and pi-go projects (31 rooms, 24 archived in one batch). The skill said "archive" but not what it does, so the agent had to read the hub source to know it was a snapshot plus a status flip and whether it could be undone. Half the archived rooms had no pinned synthesis, and the skill's table only covered "resolved + synthesized".
- **Class:** incomplete.
- **Change:** (1) New "What archiving does" section, checked against `ArchiveRoom` in mcp-server/internal/council/summary.go: snapshot to `archives/<room-id>.md`, status `resolved`, linter tags stripped, room and messages kept, undo with `signal_status(active)`; the snapshot Summary is only the last `decision` and `action`; never `delete=true` on a janitor pass. (2) Two table rows for resolved rooms without a synthesis: archive when they have a final decision or action, hold back when they have neither. (3) New "Bulk pass" section: read active/stale first, archive last, parallel batches, `mark_read_self`; ask once before archiving in an interactive "tidy" request, never in a scheduled pass. 126 -> 163 body lines; description unchanged.
- **Evidence:** rubric v2, self-scored by the editing agent (not independent): 87 -> 90 (B1 +1, C2 +1, C3 +1; A, D, E, F unchanged). Validator valid, no warnings. Evals, `claude plugin eval --case <name> --ablation none --no-publish`, 3 runs each on the final text: fires-tidy 3/3, fires-needs-synthesis 3/3, quiet-git-cleanup 3/3, quiet-new-room 3/3. fires-groom-weekly is unstable and the comparison is inconclusive: outcome passes old 5/6 then 3/6 (8/12, plus one run where the skill did not load), new 3/6, 2/6 after a scoping edit, and 3/6 for a variant without the bulk-pass section (8/18 combined). Failing answers ask scheduling questions (cloud routine vs local launchd, which rooms) instead of laying out the pass. Not separable at this n, so the per-case gate is not cleanly passed.
- **Outcome:** Accepted with a known open item: fires-groom-weekly was already flaky. Tried a plan-first rewrite of the Cadence section (pass in three lines, then /schedule or /loop, at most one question); 2/6 outcome passes, no better than before, and reverted. The failing runs ignore it: they follow the harness `/schedule` skill's own interview (cloud routine reachability, time, rooms, model) and never describe the pass, so the lever is the case or its grader, not this skill's text. The rewrite also stated unverified facts about cloud routines and `/loop` syntax. Resolved by changing the case, not the skill: the prompt "can you groom our council hub rooms every friday automatically?" became "what would you do each friday to groom our council hub rooms, and how would we have it run automatically?" so it asks for the pass instead of inviting the `/schedule` interview. Result, 6 runs each, `--ablation none`: new skill 6/6, old skill (HEAD) 6/6. The case is stable and shows the edit does not regress it, but it does not separate old from new, and the earlier results on the old prompt are not comparable. The embedded `council://janitor` copy in mcp-server/internal/handlers/resources.go still has the old text; updating it needs a server release.
